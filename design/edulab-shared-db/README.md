# 현주에듀랩 공유 Supabase 문의 기능 설계

## 결론과 작업 상태

- 기존 **PRODUCTION `ai-education-hub-dev`** (`uenvjqgylrevujdjpfed`, Tokyo)를 계속 사용한다. 이름의 `dev`는 테스트 환경이라는 뜻으로 해석하지 않는다.
- 이번 결과물은 **분석·설계·승인 대기 SQL·테스트 계획**이다. DB에 SQL을 실행하지 않았고 새 프로젝트·계정·테이블을 만들지 않았다.
- 원본 분석 브랜치: `origin/codex/backend-phase1-supabase`, 기준 커밋 `0eeccd6`.
- 결과물 브랜치: `codex/edulab-shared-db-plan`. 별도 worktree에서 작성했다. `main`·원본 분석 브랜치·운영 사이트·환경변수는 변경하지 않는다.
- 생성 SQL은 `design/` 아래에 있어 Supabase 일반 마이그레이션 폴더의 자동 적용 대상이 아니다. 이 브랜치를 운영에 병합·배포하지 않는다.

## 필요한 테이블

| 이름 | 판단 | 이유 |
|---|---|---|
| `public.edulab_inquiries` | 필요 | 홈페이지 공개 문의와 동의·보관기한·처리 상태 저장 |
| `public.edulab_admins` | 필요 | 다른 사이트 관리자와 분리된 명시적 문의 권한 명부. 자동 등록 없음 |
| `public.edulab_inquiry_history` | 상태 변경 기능을 포함하므로 필요 | 접수·상태 변경·처리자를 한 이력으로 기록. 기존 브랜치의 중복 이벤트/감사 테이블을 하나로 통합 |

문의 접수만 하고 상태 변경을 제공하지 않는 범위로 축소한다면 이력 테이블은 후속 단계로 미룰 수 있다. 이번 안은 분석 브랜치의 `received → reviewing → answered` 기능을 유지하는 3개 테이블 설계다. 별도 감사 로그·담당자·설정·알림 큐·첨부파일·정책 테이블은 만들지 않는다.

## 초보자용 진행 순서

| 순서 | 현주님이 Supabase 등에서 할 일 | Codex가 할 일 |
|---|---|---|
| 1. 지금 | **실행할 SQL 없음.** 기존 프로젝트 이름과 Ref가 위 값인지 확인 | 지정 브랜치와 DB 메타데이터를 읽기 전용으로 분석하고 이 설계 제공 |
| 2. 기준 확정 | 수집할 연락처, 개인정보 안내문·버전·보관일수, 문의 관리자 계정, 상태 관리 포함 여부 결정 | 확정 내용을 반영하고 생성·롤백 SQL의 전체 영향 범위를 다시 제시 |
| 3. 승인 전 | 새 프로젝트 생성·기존 SQL 재실행·운영 키 변경·`db push` 금지. 관리자 비밀번호/비밀키는 채팅에 보내지 않음 | `main`에 합치지 않고 기능 코드를 별도 브랜치에서 준비. 외부 남용 방지 서비스가 필요하면 비용·개인정보 처리 범위 별도 확인 |
| 4. 복구 준비 | 프로젝트의 백업 시각과 복원 가능 여부 확인. 공유 프로젝트 전체 복원이 다른 서비스도 되돌린다는 점 확인 | 기존 구조·뷰·권한·기본 권한·이벤트 트리거를 읽기 전용으로 재확인하고 충돌·백업 범위 검토. 현재 미확인 항목을 먼저 해소 |
| 5. 로컬 검증 | 새 Supabase 클라우드 프로젝트 생성 불필요 | 별도 승인된 로컬 환경에서 생성·권한·동시성 시험. Production 데이터 복제 없이 가짜 데이터 사용 |
| 6. 생성 승인 | 최종 SQL의 **운영 DB 적용만** 명시적으로 승인 | 승인된 SQL 하나만 대상 Ref에 적용. 예전 테스트용 전체 마이그레이션은 실행하지 않음 |
| 7. 관리자 지정 | Supabase Auth에서 이미 존재하고 이메일 인증된 지정 계정의 UUID 확인. 승인된 방법으로 `edulab_admins`에만 명시적으로 등록·활성화 | UUID·활성 상태·인증 상태를 검증하는 최소 작업을 별도 검토·승인 범위에 포함. 다른 관리자 명부를 복사하지 않음 |
| 8. 연동·검수 | 환경설정이 필요하면 Vercel의 해당 환경에 직접 Secret 입력. Preview도 같은 Production DB를 쓰므로 실제 쓰기 시험은 별도 승인 | 서버 저장 코드·전용 관리자 권한 연결, RLS 음성 시험, 운영 보호 및 남용 방지 검증. 브라우저에는 비밀키 전달 안 함 |
| 9. 공개 승인 | 통합시험 결과를 확인하고 `main` 병합·운영 배포·문의 접수 활성화를 각각 승인 | 승인된 변경만 반영하고 실제 접수/관리 기능 검증. 장애 시 먼저 기능을 끄고 데이터를 보존 |

Supabase SQL Editor를 직접 사용하는 경우에도 6단계 최종 승인 후 **생성 SQL 한 파일 전체만** 실행한다. 표 편집기로 임의 생성하면 RLS·권한·함수가 빠질 수 있다. Codex가 적용하기로 정했다면 같은 SQL을 중복 실행하지 않는다.

## 반드시 구분할 사항

- `edulab_`는 이름 충돌 방지 수단이다. 다른 사이트의 일반 로그인 관리자는 전용 명부에 없으면 접근하지 못하도록 RLS로 분리한다.
- 프로젝트 소유자, DB 관리자, `service_role` 비밀키 보유 서버까지 서로 격리하는 물리적 보안 경계는 아니다. 특히 프로젝트 공통 비밀키는 RLS를 우회하므로 다른 사이트 서버의 키 보관 수준도 중요하다. 더 강한 분리가 필요하면 별도 최소 권한 DB 역할·접속 방식 설계가 추가로 필요하다.
- 현재 운영 테이블에 문제가 있다고 판단해도 이 작업에서 고치거나 초기화하지 않는다. 미확인 뷰·권한을 추정으로 변경하지 않는다.
- 생성 SQL 승인, 관리자 지정, 실제 시험 데이터 생성·삭제, 기능 공개, 롤백은 서로 다른 승인 범위다.
